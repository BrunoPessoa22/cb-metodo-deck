Hub para empresas — spec técnica F0–F4

O hub hoje é single-player B2C. O pivô exige a camada de empresa: organizações, assentos, áreas, faixas com revisão, Builder Score e painel do sponsor. Esta spec traz modelo de dados, telas e critérios de aceite por fase — varredura completa da API pública em 17/08 confirmou que nenhum desses conceitos existe em produção hoje.

F0Acesso e descoberta — bloqueia tudo (esta semana)

O código do hub não está com o resto dos repositórios. O que sabemos por fora: Next.js atrás de Cloudflare, identidade via Stack Auth (/handler/*), vídeo via api.video, pagamentos Stripe + Asaas + Gotas, entitlements concedidos por rota a partir do plano individual (/api/subscription/plans).

Perguntas que a call de descoberta precisa responder:

  1. Onde está o repo e qual o fluxo de deploy? Acesso de leitura para o time do Método.
  2. Schema atual do banco (dump) — especialmente user, subscription, progress, projects, badges.
  3. Stack Auth suporta organizações/teams nativamente na versão usada? (Stack Auth tem primitives de teams — se estiverem disponíveis, F1 encurta.)
  4. Billing: os planos são escalares hoje; existe caminho para quantidade (assentos) no Stripe/Asaas sem reescrever o checkout?
  5. Feature flags / entitlements: como adicionar gate por empresa além do gate por plano individual?
  6. Dois SKUs B2B quebrados hoje: R$ 297 sem allowed_payment_methods e R$ 499,90 expirado em 11/08 sem features — decidir se conserta ou remove do checkout público.

Regra inegociável: nenhum segundo login. A camada de empresa consome a identidade Stack Auth existente. Se F1 nascer como app separado com auth próprio, criamos para sempre o problema de assinante com duas contas. Referência de schema pronta para adaptar: repo builders-club (companies/users/enrollments/lesson_progress com RLS por empresa) — usar como referência de modelo, não como segunda plataforma.

F1Camada de empresa — organizações, assentos, áreas (5–8 dev-dias)

Modelo de dados

companies      id · nome · cnpj · plan · seats_total · sponsor_user_id · created_at
departments    id · company_id · nome
               (seed: Comercial, Marketing, Financeiro, RH, Jurídico, Operações, TI, Outro)
users          + company_id (nullable — B2C segue sem empresa)
               + department_id (nullable)
               + org_role: member | org_admin | sponsor
invites        id · company_id · email · department_id · token · status · expires_at

Telas

  • Admin CB: criar empresa, definir assentos, designar sponsor e org_admin (entra no admin existente do hub).
  • Org admin: convidar por e-mail individual ou CSV; ver assentos usados/livres; tag de área por pessoa.
  • Membro convidado: aceita via magic link → cai no onboarding existente com department pré-preenchido.

Critérios de aceite

  • Convite aceito consome 1 assento; assentos esgotados bloqueiam novo convite com mensagem clara ao org_admin.
  • Usuário B2C existente pode ser “adotado” por uma empresa sem perder progresso, faixas ou histórico (caso real: funcionários de clientes já têm conta PF).
  • Entitlement por empresa: todo assento ativo acessa o conteúdo Premium enquanto o contrato da empresa estiver ativo, independente de assinatura individual.
  • Remover pessoa da empresa devolve o assento e rebaixa o acesso dela para o plano individual que tiver (ou free).

F4Diagnóstico por área — antes de F2/F3 na ordem de build (4–6 dev-dias)

(Fora de ordem de propósito: destrava vendas e gera o Builder Score Zero — e só depende de F1.)

Base existente

  • O hub já tem um motor de onboarding com 164 respostas estruturadas (admin → onboarding-insights). É extensão, não criação.
  • Instrumento por área já validado em cliente real: modelo Klini — por departamento: responsável, tamanho do time, horas perdidas em trabalho manual, sistemas usados, dor 0–12, três quick wins. Motor de pontuação com pesos pronto no repo builders-club (diagnostic-engine.ts).

Modelo de dados

diagnostic_instances   id · company_id · department_id · respondent_user_id (ou e-mail externo)
                       · status · created_at
diagnostic_answers     instance_id · question_id · answer (jsonb)
diagnostic_questions   + department_scope (null = geral)

Critérios de aceite

  • Org admin dispara o diagnóstico por área (link por e-mail, sem exigir conta para responder).
  • Saída 1: relatório por empresa consolidado (briefing dos professores + versão para o sponsor).
  • Saída 2: Builder Score Zero gravado como primeiro snapshot (ver F3) no D-7 do contrato.
  • Dores por área ficam consultáveis agregadas entre empresas (insumo de playbooks e add-ons) — anonimizadas fora da empresa dona.

F2Faixas + registro de artefatos (8–12 dev-dias)

Base existente — estender, não criar

  • Builders Projects (113 projetos) já é submissão com categorias, senioridade e votos → vira o registro de artefatos.
  • Badges por curso + streaks já existem no perfil → a faixa entra como badge de tipo novo, com regra própria.

Modelo de dados

belt_levels    seed das 4 faixas (Operador, Construtor, Builder, Embaixador) + criteria (texto da rubrica)
artifacts      id · user_id · belt_level_id · title · description · evidence_url
               · usage_evidence (quem usa, desde quando) · status: submitted|approved|rejected
               · reviewer_id · feedback · submitted_at · reviewed_at
belt_awards    IMUTÁVEL: id · user_id · belt_level_id · artifact_id · awarded_at

Fluxo e telas

  • Submissão: formulário no perfil (título, descrição, link de evidência, evidência de uso). Rubrica visível na própria tela.
  • Fila de revisão: página para revisores (professores/CB, papel reviewer) — pendências ordenadas por idade, aprovação/reprovação com feedback obrigatório, SLA 5 dias úteis com alerta de estouro.
  • Aprovação → cria belt_award → badge de faixa no perfil → notificação ao usuário e ao org_admin.
  • Trilhas async com gate por faixa. Mapeamento inicial do catálogo atual (119 aulas): cursos iniciante/primeiro-app → trilha Operador · profissional/intermediário → Construtor · avançado/negócio/Claude Code → Builder.

Critérios de aceite

  • Fluxo completo submissão → revisão → badge funcionando de ponta a ponta, com trilha de auditoria (quem aprovou o quê, quando).
  • Perfil público do membro mostra a faixa (é o selo que ele leva pro LinkedIn — parte do produto).
  • Org admin e sponsor veem as faixas de todos os assentos da empresa, por área.
  • Award é imutável: revogação só por fraude, via registro administrativo separado, nunca deleção.

F3Builder Score + painel do sponsor (5–8 dev-dias)

Modelo de dados

company_score_snapshots   id · company_id · period (semana ISO)
                          · active_seats_pct        (assentos com login+ação na semana / total)
                          · artifacts_in_production (belt_awards Builder+ ativos)
                          · depts_with_build_pct    (áreas com ≥1 build / áreas com assento)
                          · embaixadores_count
                          · score (composto v1)
                          · created_at

Fórmula v1 (ajustável, versionada): score = 40%·assentos_ativos + 30%·áreas_com_build + 20%·builds_em_produção(normalizado) + 10%·embaixadores. Job semanal agendado. Snapshots desde o primeiro dia — nunca só o valor atual: o produto de renovação é a curva D0 → D365, e sem histórico ela não existe.

Painel do sponsor

  • Rota read-only por empresa (papel sponsor): score atual + tendência, quebra por área, lista de builds em produção (título, área, impacto declarado), nº de pessoas por faixa, próximos marcos da temporada.
  • Export em PDF (vira anexo do relatório trimestral do Success).
  • Protótipos de referência prontos nos repos locais: builders-club (admin/empresas/[id] — visão por área com dores) e enterprise-ai-academy (conclusão por departamento, colaborador em risco).

Critérios de aceite

  • Snapshot semanal gerado automaticamente para toda empresa ativa; falha do job alerta o time.
  • Sponsor enxerga apenas a própria empresa; dados individuais além de faixa/atividade agregada não vazam (assiduidade individual é sensível — mostrar por área, não por pessoa, exceto para org_admin).
  • Builder Score Zero (do F4) aparece como primeiro ponto da curva.

+Backlog paralelo (fora das fases, quando couber)

  • Billing por assento: hoje os planos são preços escalares; o contrato B2B precisa de quantidade (15 assentos ref.). Curto prazo: cobrar fora do hub (fatura) e provisionar assentos manualmente via F1; médio prazo: quantity no gateway.
  • Conta de serviço para o publisher do feed (hoje o bot posta como a conta pessoal/admin — item de segurança já reportado).
  • Correções cosméticas com cara de quebrado: © 2025 no rodapé, timer de escassez marcando 704 dias.
  • SKUs B2B quebrados: decidir consertar ou remover (ver F0.6).
  • API de leitura para o Score (futuro: alimentar relatórios e a página do sponsor externa sem scraping).

Riscos principais: (1) plataforma dupla — qualquer atalho “fora do hub com login próprio” é dívida permanente; (2) identidade/billing do hub terem acoplamentos não visíveis por fora — por isso F0 vem antes de qualquer estimativa virar compromisso; (3) fila de revisão sem dono vira gargalo — o SLA é de gente, não de código (dono: Head de Success).
